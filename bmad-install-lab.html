Esercitazione 0

Prerequisiti

Quattro cose obbligatorie e una che serve solo all'orchestratore. Scegli il tuo sistema in alto: tutta la pagina si adatta.

Sistema:
ComponenteObbligatorioA cosa serve
Node.js 20.12+sìServe solo a far girare l'installer. Il metodo, una volta installato, non usa Node.
uv + Python 3.11+sìGli script di supporto delle skill girano con uv run. Dalla 6.11 non c'è più un ripiego su un interprete di sistema: senza uv, alcune skill si arrestano. È anche il modo più semplice di installare l'orchestratore.
GitsìPer clonare i moduli esterni durante l'installazione, e per l'isolamento in worktree dell'orchestratore.

macOS

Il percorso più liscio passa da Homebrew. Se non ce l'hai, installalo prima dal sito ufficiale.

Prerequisiti su macOS
# Node, git e il multiplexer
brew install node git tmux

# uv — provvede da sé un Python adatto, non serve installarlo a parte
curl -LsSf https://astral.sh/uv/install.sh | sh

# riapri il terminale, poi verifica tutto in un colpo
node --version    # atteso: v20.12.0 o superiore
git --version
uv --version
tmux -V
Se node è troppo vecchio È il problema numero uno su macchine con progetti di età diversa. Un gestore di versioni risolve una volta per tutte: brew install nvm oppure brew install fnm, poi installi la 20 o superiore e la imposti come predefinita. Verificalo prima di lanciare l'installer: l'errore che dà altrimenti non è sempre limpido.
Windows + WSL — la strada consigliata

Per questi strumenti WSL è Linux: tutti i percorsi POSIX e tmux funzionano senza modifiche, e nulla del setup cambia. È l'opzione da preferire in aula, perché elimina un'intera classe di problemi.

1 · Preparare WSL (da PowerShell come amministratore)
wsl --install -d Ubuntu
# riavvia se richiesto, poi apri Ubuntu e crea il tuo utente
2 · Prerequisiti dentro Ubuntu
sudo apt update
sudo apt install -y git tmux curl

# Node 20+ — il pacchetto di Ubuntu è spesso troppo vecchio
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
sudo apt install -y nodejs

# uv
curl -LsSf https://astral.sh/uv/install.sh | sh

# riapri la shell e verifica
node --version; git --version; uv --version; tmux -V
La regola d'oro di WSL Lavora dentro il filesystem di Linux (~/progetti/…), non su /mnt/c/…. Attraversare il confine fra i due filesystem è lento in modo drammatico e crea problemi di permessi che si manifestano come errori incomprensibili. Clona i repository dentro WSL, non in Windows.
Installa gli strumenti nell'interprete Linux Una versione di questi strumenti installata su Windows è raggiungibile dal prompt bash e si comporta silenziosamente come Windows. Per l'orchestratore c'è un modo di verificarlo: il comando che elenca i backend del multiplexer deve dire che il default di piattaforma è linux. Se dice win32, stai usando la build sbagliata.
Windows nativo

Funziona, con un'avvertenza importante: il metodo gira benissimo, l'orchestratore è sperimentale. Il backend nativo esiste — una reimplementazione di tmux su ConPTY — ma il progetto dichiara che non è ancora al livello di supporto di Linux, macOS e WSL: restano da completare l'ospitalità delle finestre e l'aggancio e sgancio delle sessioni.

Prerequisiti con winget (da PowerShell)
winget install OpenJS.NodeJS.LTS
winget install Git.Git
winget install astral-sh.uv
winget install Microsoft.PowerShell

# riapri PowerShell e verifica
node --version
git --version
uv --version
pwsh --version
Per l'orchestratore, in più Servono psmux e pwsh raggiungibili nel PATH, con psmux in versione superiore alla 3.3.6 — le versioni fino a quella possono terminare a forza un processo riciclato durante lo smontaggio, e per questo vengono considerate non disponibili. Il backend viene selezionato da solo su Windows quando questi prerequisiti ci sono.
Consiglio per l'aula Se la giornata prevede l'esercitazione sull'orchestratore, fai preparare WSL a tutti i partecipanti Windows. Il Windows nativo va benissimo per le esercitazioni da 1 a 4 e per la 7, ma sulla 5 rischi di passare il tempo a diagnosticare il multiplexer invece che a insegnare.

Prima di qualunque comando: dove lavorare. Tutte le esercitazioni presuppongono un repository usa-e-getta. Questi strumenti scrivono file, eseguono comandi e committano. In aula non si punta mai nulla di questo su codice di lavoro, e nemmeno su un progetto personale a cui si tiene. Un clone nuovo, un branch dedicato, e la libertà di cancellare tutto.

ES · 1
Installare il metodoUn progetto vuoto, un comando, sei domande
15 min▶
Obiettivo. Portare a termine un'installazione interattiva, capendo cosa chiede ogni domanda. Poi ripeterla in forma non interattiva, che è quella che userai davvero.

Passo 1 — Un progetto pulito

macOS · terminale
mkdir ~/bmad-lab && cd ~/bmad-lab
git init
WSL · dentro il filesystem Linux, non su /mnt/c
mkdir ~/bmad-lab && cd ~/bmad-lab
git init
Windows · PowerShell
mkdir $HOME\bmad-lab; cd $HOME\bmad-lab
git init

Passo 2 — Guardare l'elenco degli strumenti supportati

Prima di installare, vale la pena vedere la lista completa con le rispettive cartelle di destinazione. È la stessa tabella della parte 1, ma aggiornata alla versione che stai per installare.

Elenco degli strumenti
npx bmad-method install --list-tools

Passo 3 — L'installazione interattiva

Il comando principale
npx bmad-method install

Ti verranno poste fino a sei domande. Vale la pena fermarsi su ciascuna invece di premere invio:

  1. Cartella di installazione. Predefinita: quella corrente. Accettala.
  2. Quali moduli. Caselle per core, bmm, bmb, cis, gds, tea. Per ora solo bmm: core viene aggiunto da solo e installato per primo. Aggiungeremo bmb nell'esercitazione 5.
  3. Tutto stabile? Rispondi sì: accetta l'ultimo tag rilasciato per ogni modulo esterno.
  4. Con quali strumenti integrare. Scegli la CLI che userai davvero. È la risposta che determina in quale cartella finiranno le skill.
  5. Configurazione del modulo. Nome, lingua, cartella di output. Qui si decidono i percorsi degli artefatti: annota cosa rispondi, serve nell'esercitazione 2.
  6. Installare gli shim di compatibilità? Su un'installazione nuova la risposta predefinita è no, ed è quella giusta: sono inoltri per skill deprecate che ti servono solo se stai migrando da una versione precedente.

Passo 4 — La stessa cosa, in forma riproducibile

La forma interattiva serve a capire. Quella da usare per davvero — in aula, negli script, nella CI — è quella con i flag: è ripetibile e documenta da sola cosa è stato installato.

Installazione non interattiva
npx bmad-method install --directory . --modules bmm --tools claude-code --yes

Adatta --tools alla tua CLI. Gli identificatori validi sono quelli stampati da --list-tools.

Da far notare in aula --modules non è un delta: elenca l'insieme esatto che vuoi avere alla fine. Se in seguito lanci lo stesso comando con un modulo in meno, quel modulo viene rimosso. È la causa più frequente di «mi è sparito un modulo» dopo un aggiornamento fatto di fretta.
Se l'installazione riesce ma la prima skill si arresta È uv mancante. L'installer stampa un avviso e nomina le skill che si fermeranno, ma non blocca: puoi vedere un'installazione verde e trovarti bloccato al primo comando. Installa uv, riapri il terminale e riprova — non serve reinstallare BMAD.

Ispezionare cosa è stato scrittoL'esercitazione che vale più di tutta la teoria
20 min▶
Obiettivo. Guardare con i propri occhi le cartelle create, capire cosa c'è dentro ciascuna e decidere consapevolmente cosa committare. Chi salta questo passaggio non saprà mai diagnosticare un problema.
macOS · guarda cosa è comparso
# tutte le cartelle nascoste create
ls -la

# le skill: una cartella ciascuna
ls .claude/skills/          # o .agents/skills/ per altri strumenti

# dentro una skill
ls .claude/skills/bmad-build/
head -20 .claude/skills/bmad-build/SKILL.md

# cosa c'è in _bmad — nota: NIENTE skill
find _bmad -maxdepth 2 -type d

# quante skill sono state installate
ls .claude/skills/ | wc -l
WSL · identici a macOS
ls -la
ls .claude/skills/
ls .claude/skills/bmad-build/
head -20 .claude/skills/bmad-build/SKILL.md
find _bmad -maxdepth 2 -type d
ls .claude/skills/ | wc -l
Windows · PowerShell
Get-ChildItem -Force

Get-ChildItem .claude\skills\
Get-ChildItem .claude\skills\bmad-build\
Get-Content .claude\skills\bmad-build\SKILL.md -TotalCount 20

Get-ChildItem _bmad -Recurse -Directory -Depth 1 | Select-Object FullName

(Get-ChildItem .claude\skills\).Count

Le cinque domande a cui rispondere guardando

  1. Dove sono finite le skill? Nella cartella dello strumento che hai scelto. Verifica che corrisponda alla riga della tabella nella parte 1.
  2. Che forma ha una skill? Apri SKILL.md: è Markdown con un frontmatter che dichiara nome e descrizione. Non è codice. Guarda anche workflow.md e i file dei passi.
  3. Cosa c'è in _bmad/? Configurazione, manifesti, script — e nessuna skill. Se te lo aspettavi diversamente, è il momento di correggere il modello mentale.
  4. La cartella _bmad/custom/ è vuota? Sì, e deve esserlo: i file compaiono solo quando personalizzi davvero.
  5. Esiste già _bmad-output/? Probabilmente no. Le cartelle degli artefatti non vengono pre-create: nascono quando la prima skill ci scrive dentro.

La decisione da prendere adesso: cosa va in git

CosaIn git?Perché
.claude/skills/ o equivalentesìChi clona il repository ottiene la stessa versione del metodo, e in code review si vede cosa cambia quando qualcuno aggiorna.
_bmad/sìConfigurazione condivisa e manifesti dell'installazione.
_bmad/**/*.user.tomlnoSono preferenze personali per definizione.
_bmad-output/decideteCommittarla significa avere la storia delle decisioni di prodotto nel repository — che è metà del valore del metodo. È una scelta di squadra, non una preferenza individuale.
.bmad-loop/noSe ne occupa da solo il comando di inizializzazione dell'orchestratore.
Esercizio bonus, molto istruttivo Fai git status e conta i file non tracciati. Poi git add -A e git status di nuovo. In aula genera sempre una discussione utile: vogliamo davvero centinaia di file di skill nella cronologia del repository? Non c'è una risposta unica — ma va discussa una volta, non subita.
ES · 3
Il primo giro di provaVerificare che l'installazione sia viva davvero
20 min▶
Obiettivo. Passare da «i file ci sono» a «funziona». Sono due cose diverse, e la seconda si verifica solo eseguendo qualcosa.
Apri la CLI nella cartella del progetto
claude       # o codex, gemini, copilot… secondo lo strumento scelto
  1. Chiedi aiuto: /bmad-help. Se risponde elencando le skill disponibili e suggerendo cosa fare, l'installazione è viva. È anche il modo giusto di orientarsi ogni volta che non si sa che passo fare.
  2. Prova un agente con nome: scrivi hey Mary, let's brainstorm. Osserva che si presenta, adotta la persona e — se l'intento è chiaro — salta il menu e parte direttamente.
  3. Prova la skill di implementazione su un compito senza incognite: /bmad-build write an implementation of mars rover kata. Rispondi alla domanda che ti fa, leggi il piano, approvalo.
  4. Torna al terminale e guarda cosa è comparso: la cartella degli artefatti adesso esiste, con dentro la specifica che la skill ha prodotto.
Cosa hai appena verificato Tre cose in una: che le skill sono nella cartella giusta perché la CLI le ha trovate; che uv funziona, perché gli script di supporto hanno girato; e che i percorsi degli artefatti configurati all'installazione sono quelli veri, perché ci è stato scritto dentro.
ES · 4
Personalizzare senza rompereIl modello a tre strati, provato su un caso reale
25 min▶
Obiettivo. Imparare l'unico posto in cui è lecito mettere le mani. Chi modifica direttamente le skill perde tutto al primo aggiornamento: questa esercitazione previene quel danno.

Il modello, in tre righe

Priorità, dalla più alta
1. _bmad/custom/{skill}.user.toml    ← personale, si ignora in git — vince
2. _bmad/custom/{skill}.toml         ← di team, si committa
3. {skill}/customize.toml            ← i default — NON si modifica
  1. Apri il customize.toml di un agente, per esempio quello del PM, e leggi cosa dichiara come personalizzabile. Non modificarlo.
  2. Crea la cartella _bmad/custom/ se non esiste, e dentro un file con il nome della skill.
  3. Scrivici solo i campi che vuoi cambiare. Copiare l'intero customize.toml è l'errore classico: al prossimo aggiornamento la tua copia congelata sovrascriverà le novità.
  4. Verifica che il merge sia avvenuto invocando l'agente e osservando il comportamento cambiato.
Esempio: fatti persistenti per il team
# _bmad/custom/bmad-agent-architect.toml
[agent]
persistent_facts = [
  "L'organizzazione è esclusivamente su AWS: nessuna proposta multi-cloud.",
  "Il database standard è PostgreSQL. Ogni deroga va motivata.",
  "La suite di test completa impiega undici minuti."
]
Le regole di merge, da conoscere Uno scalare viene sostituito. Una tabella viene fusa in profondità. Un array di tabelle in cui tutti gli elementi condividono lo stesso campo identificatore viene fuso per chiave — le chiavi che coincidono sostituiscono in loco, quelle nuove si aggiungono. Ogni altro array viene aggiunto in coda. E non esiste un meccanismo di rimozione: gli override non possono cancellare elementi di base. Se devi sopprimere una voce di menu, la sovrascrivi per chiave con una descrizione neutra.
Scorciatoia Esiste una skill di assistenza alla personalizzazione che analizza cosa è personalizzabile nella tua installazione, ti aiuta a scegliere la superficie giusta, scrive il file al posto tuo e verifica che il merge sia andato a buon fine. Utile soprattutto la prima volta, per non dover imparare la struttura TOML a mente.
ES · 5
Aggiungere un modulo: il costruttoreInstallare bmb e creare la propria prima skill
40 min▶
Obiettivo. Vedere come si aggiunge un modulo a un'installazione esistente — che è diverso da installare da zero — e capire il ciclo di creazione di una skill propria, che è il modo in cui BMAD si estende davvero.

Passo 1 — Aggiungere il modulo

Aggiunta a un'installazione esistente
npx bmad-method install --yes --action update --modules bmm,bmb

--tools si omette di proposito: l'azione di aggiornamento riusa gli strumenti configurati alla prima installazione. E ricorda che --modules è l'insieme completo: bmm va rielencato, altrimenti verrebbe tolto.

Passo 2 — Vedere cosa è cambiato

macOS / WSL
git status --short | head -30
ls .claude/skills/ | grep -i builder
WSL
git status --short | head -30
ls .claude/skills/ | grep -i builder
Windows · PowerShell
git status --short | Select-Object -First 30
Get-ChildItem .claude\skills\ | Where-Object Name -like "*builder*"

Compaiono le skill del costruttore: il costruttore di agenti, quello di workflow, quello di moduli, l'esecutore di valutazioni e la skill di setup del modulo.

Passo 3 — Creare la prima skill

Dentro la CLI
/bmad-bmb-setup

# poi, per costruire qualcosa di tuo:
/bmad-workflow-builder Voglio una skill che, dato un messaggio di errore,
produca una checklist di diagnosi ordinata dal controllo più economico
al più costoso.
  1. Rispondi alle domande del costruttore. Osserva che ti chiede l'intento prima della struttura: è la stessa logica del metodo, applicata a se stesso.
  2. Guarda dove è stata scritta la skill: il modulo chiede all'installazione dove salvare le tue creazioni, e il valore predefinito è una cartella skills/ nel progetto.
  3. Apri il SKILL.md generato e confrontalo con quello di una skill ufficiale. È lo stesso formato — lo standard aperto Agent Skills — ed è il motivo per cui la tua skill funziona anche su altri strumenti.
  4. Invoca la tua skill e provala su un caso vero.
Il collegamento con il modulo sul prompt Costruire una skill è scrivere un prompt strutturato che sopravvive alla sessione. Il modulo 1 è la teoria di cosa mettere in quel file; il costruttore è lo strumento che gli dà una forma installabile e condivisibile. È il punto in cui i due argomenti del corso si toccano.
ES · 6
Installare l'orchestratoreDue pezzi, due strade, un preflight che dice la verità
45 min▶
Obiettivo. Installare bmad-loop capendo che sono due componenti distinti — le skill e il programma — e imparare a leggere il preflight, che è lo strumento diagnostico più utile dell'intero ecosistema.
Su Windows nativo L'orchestratore gira su un backend sperimentale. Se puoi, fai questa esercitazione dentro WSL. Se proprio devi restare nativo, aspettati di dover diagnosticare il multiplexer, e usa il comando che elenca i backend per capire cosa è stato selezionato e perché.

Strada A — dal pacchetto Python (autosufficiente)

È la strada più diretta: il pacchetto include già le tre skill, e il comando di inizializzazione le mette a posto insieme agli hook e alla policy.

Strada A
# un tag fissato — riproducibile, consigliato per l'uso quotidiano
uv tool install "bmad-loop[tui] @ git+https://github.com/bmad-code-org/bmad-loop.git@v0.9.1"

# oppure la punta del ramo principale: più funzionalità, meno stabile
# uv tool install "bmad-loop[tui] @ git+https://github.com/bmad-code-org/bmad-loop.git"

bmad-loop --version

cd ~/bmad-lab
bmad-loop init --cli claude       # ripetibile con --cli codex, --cli gemini…
bmad-loop validate

L'extra [tui] aggiunge la dashboard; si può omettere per un'installazione senza interfaccia.

Strada B — dal selettore dell'installer BMAD

Se hai selezionato il modulo nel picker, l'installer ha copiato solo le skill. Il programma va ancora installato, e lo fa la skill di setup.

Strada B
# 1 · aggiungi il modulo all'installazione
npx bmad-method install --yes --action update --modules bmm,bmad-loop

# 2 · completa: installa il programma, sceglie le CLI, registra gli hook, fa il preflight
claude "/bmad-loop-setup accept all defaults"

Passo comune — leggere il preflight

Il comando diagnostico più utile
bmad-loop validate

# quale multiplexer è stato scelto, e perché
bmad-loop mux

# quali adattatori di CLI sono registrati
bmad-loop adapters

Il preflight controlla, uno per uno: la configurazione BMAD, la presenza di uno sprint-status.yaml, git, il binario della CLI, la registrazione degli hook e lo stato del multiplexer. Verifica inoltre che ci siano le skill che l'orchestratore andrà a invocare, e le segnala con l'indicazione di quale modulo le fornisce se mancano.

Il preflight fallirà, ed è previsto A questo punto manca sprint-status.yaml, perché non hai ancora fatto pianificazione. È il modo giusto per far vedere che il preflight controlla davvero invece di dire sempre di sì. Per completare, servirebbe una passata di pianificazione — che è l'argomento del laboratorio sui tre flussi, non di questa pagina.
Il passaggio che tutti dimenticano, e che costa mezz'ora Se la CLI di coding non è mai stata avviata in quel progetto, avviala una volta a mano e accetta la finestra di fiducia del workspace e l'eventuale approvazione degli hook. Una sessione generata dall'orchestratore non può rispondere a un dialogo di primo avvio, e quel blocco viene letto come un timeout di sessione: un sintomo che non suggerisce affatto la sua causa.

Cosa è comparso sul disco

macOS / WSL
ls -la .bmad-loop/
cat .bmad-loop/policy.toml | head -30
git diff .gitignore
ls ~/.local/state/bmad-loop/ 2>/dev/null
WSL
ls -la .bmad-loop/
cat .bmad-loop/policy.toml | head -30
git diff .gitignore
ls ~/.local/state/bmad-loop/ 2>/dev/null
Windows · PowerShell
Get-ChildItem -Force .bmad-loop\
Get-Content .bmad-loop\policy.toml -TotalCount 30
git diff .gitignore
Get-ChildItem $env:LOCALAPPDATA\bmad-loop\state\ -ErrorAction SilentlyContinue

Nota due cose: il .gitignore è stato modificato — guarda il diff prima di committare — e nella tua home è comparsa una radice di stato fuori dall'albero di progetto, che è deliberato: un cambio di branch o un rollback non devono poter togliere il piano di controllo a un run vivo.

ES · 7
Aggiornare un'installazione esistenteDue assi, tre canali, e un menu che va capito
30 min▶
Obiettivo. Aggiornare senza sorprese. È l'operazione che si fa più spesso dopo la prima installazione, e quella su cui si sbaglia di più — perché il versionamento ha due assi indipendenti che vanno tenuti distinti.

I due assi, da tenere separati in testa

AsseCosa controllaCome lo muovi
Versione dell'installerLe versioni di core e bmm, che viaggiano dentro il pacchetto npmnpx bmad-method install per la stabile, npx bmad-method@next install per la prerelease. Non esiste altro modo: un pin su bmm è inefficace, e l'installer te lo dice.
Canale dei moduli esterniTutti gli altri moduli, che vengono clonati da GitTre canali per modulo: l'ultimo tag rilasciato, la punta del ramo principale, oppure un tag fissato. Si possono mescolare liberamente.

Il menu che appare se la cartella contiene già _bmad/

SceltaCosa fa
Quick UpdateRilancia l'installazione con le impostazioni esistenti. Rinfresca i file, applica patch e aggiornamenti minori stabili, rifiuta gli aggiornamenti maggiori. Veloce e non interattivo. È quello che vuoi il 90% delle volte.
Modify InstallFlusso interattivo completo. Aggiungi o rimuovi moduli, riconfiguri le impostazioni, e — se rispondi di sì alla domanda apposita — rivedi e cambi il canale di ogni modulo esterno.
  1. Lancia npx bmad-method install nel progetto già installato e osserva che compare il menu invece delle domande iniziali.
  2. Scegli Quick Update e guarda cosa cambia con git status. Nota che le tue personalizzazioni in _bmad/custom/ non vengono toccate.
  3. Rilancia scegliendo Modify Install e rispondi di sì alla revisione dei canali: per ciascun modulo esterno ti verrà offerto di mantenere, passare a stabile, passare alla punta del ramo o fissare un tag.
  4. Osserva come vengono classificati gli aggiornamenti disponibili.
La regola sugli aggiornamenti maggiori Patch e minori vengono proposti con risposta predefinita affermativa; i maggiori con risposta predefinita negativa, perché le rotture di compatibilità si presentano spesso come «instabilità» quando non ci si aspettava un cambio maggiore. La richiesta include un collegamento alle note di rilascio: leggile prima di accettare. In modalità non interattiva patch e minori si applicano da soli, i maggiori restano fermi finché non li accetti esplicitamente fissando il nuovo tag.

Ricette non interattive

Le quattro che servono davvero
# tutto stabile, insieme esatto di moduli
npx bmad-method install --yes --modules bmm,bmb,cis --tools claude-code

# riproducibile byte per byte — installazioni aziendali e CI
npx bmad-method install --yes --modules bmm,bmb,cis \
  --pin bmb=v1.7.0 --pin cis=v0.2.0 --tools claude-code

# punta del ramo per i moduli esterni
npx bmad-method install --yes --modules bmm,bmb --all-next --tools claude-code

# aggiungere un modulo mantenendo il resto (--tools si omette apposta)
npx bmad-method install --yes --action update --modules bmm,bmb,gds

La precedenza quando i flag si sovrappongono: il pin batte la punta del ramo per singolo modulo, che batte l'impostazione globale, che batte il default del registro.

Gli shim di compatibilità

Quando una skill viene deprecata, resta in vita come inoltro verso quella nuova. L'aggiornamento ti chiede se vuoi tenerli, con risposta predefinita affermativa perché premere invio non deve mai rompere una skill che stai usando. Ogni volta che li mantiene, l'installer elenca quali sono e verso cosa inoltrano: è la tua lista di migrazione.

Toglierli quando hai finito di migrare
npx bmad-method install --yes --action update --modules bmm --no-shims

Aggiornare l'orchestratore — sono due passi, non uno

La strada facile
claude "/bmad-loop-setup upgrade"
I due passi che quella skill esegue — utili per CLI diverse o per script
# 1 · il programma. --reinstall è NECESSARIO su una sorgente git:
#     un upgrade normale riusa il commit in cache e non prende il codice nuovo
uv tool upgrade bmad-loop --reinstall

#     per passare a un tag più nuovo, reinstalla nominandolo
# uv tool install --force "bmad-loop[tui] @ git+https://github.com/bmad-code-org/bmad-loop.git@v0.9.1"

# 2 · le copie delle skill in OGNI progetto che usa l'orchestratore
#     init le ha congelate all'installazione: l'upgrade del programma non le tocca
bmad-loop init --project /percorso/del/progetto --force-skills
I due errori classici sull'aggiornamento dell'orchestratore Il primo: dimenticare il secondo passo, e restare con skill vecchie che parlano con un programma nuovo. Il secondo: omettere --reinstall su una sorgente git, e credere di aver aggiornato mentre il commit in cache è lo stesso di prima. Il file di policy invece sopravvive intatto: le chiavi nuove sono opzionali e ricadono sui propri default.

A · Moduli veri — si aggiungono dal selettore

Provane uno che non hai ancora
# suite creativa e architetto dei test, insieme a quelli che hai già
npx bmad-method install --yes --action update --modules bmm,bmb,cis,tea

# quali chiavi di configurazione espone un modulo
npx bmad-method install --list-options cis

Esiste anche la possibilità di installare moduli di comunità da un URL Git o da un percorso locale, con l'apposito flag di sorgente personalizzata. È il meccanismo con cui un'organizzazione distribuisce i propri moduli interni.

B · Sistemi che vivono accanto — si installano, ma non dentro BMAD

Il caso più interessante da mostrare in aula è boss-skill: non è un addon, è un sistema alternativo che risolve lo stesso problema con un'architettura diversa. Trasforma un assistente in una squadra — PM, architetto, designer, tech lead, scrum master, frontend, backend, QA, DevOps — e la sua tesi è esplicitamente costruita contro l'orchestrazione basata solo su prompt: stato a runtime, eventi in sola aggiunta, gate non aggirabili, valutazioni deterministiche, artefatti riproducibili.

Installazione da npm — in un progetto separato
# NON nello stesso progetto in cui hai BMAD: sono due sistemi
mkdir ~/boss-lab && cd ~/boss-lab && git init

# una tantum, senza installazione globale
npx @blade-ai/boss-skill

# oppure globale, con la procedura guidata di auto-installazione
# npm install -g @blade-ai/boss-skill && boss-skill install

# prova prima cosa farebbe, senza scrivere niente
# boss-skill install --dry-run
# boss-skill uninstall     ← per ripulire a fine esercitazione

# poi, dentro la CLI, prova un singolo ruolo invece dell'intera pipeline
# /boss:plan   → PM + architetto
# /boss:review → revisione in sola lettura
Esercizio comparativo, molto formativo Dai la stessa consegna a BMAD e a boss-skill in due progetti separati, e confronta gli artefatti prodotti: dove finiscono, che forma hanno, quanto sono verificabili. Non serve a decretare un vincitore — serve a far vedere che «metodo strutturato per agenti» è ormai una categoria con più implementazioni, e che le differenze stanno nella forma delle prove che ciascuno lascia.

C · Porting su altre piattaforme

Se in aula qualcuno usa OpenClaw, esiste un porting del metodo come plugin di quella piattaforma, con strumenti propri per inizializzare il progetto, elencare e avviare i workflow, salvare gli artefatti e leggere lo stato. Non si installa con l'installer BMAD: si clona nella cartella delle estensioni della piattaforma e si dichiara nella sua configurazione.

Il dettaglio di progettazione da raccontare Il master deve essere un agente di primo livello e non un sotto-agente, perché in quella piattaforma i sotto-agenti non possono generarne altri — e il master deve poter generare gli specialisti. È un ottimo esempio di come i vincoli della piattaforma sottostante si riflettano nell'architettura dell'imbracatura.

Rimuovere tutto, pulitoSaper disinstallare è parte del saper installare
15 min▶
Obiettivo. Riportare il progetto allo stato iniziale. Serve a due cose: liberare la macchina d'aula fra una sessione e l'altra, e — soprattutto — verificare di aver capito davvero cosa era stato scritto e dove.

L'orchestratore, che ha una procedura propria

La documentazione del progetto descrive una procedura di rimozione che inverte quello che l'inizializzazione aveva messo: stato, skill, hook, voci del .gitignore, e infine la disinstallazione del programma. È l'ordine corretto, perché rimuovere prima il programma lascia gli hook registrati che poi falliscono in silenzio.

Il programma, dopo aver ripulito i progetti
uv tool uninstall bmad-loop

Il metodo — a mano, ed è istruttivo

macOS / WSL · esercizio a memoria, prima di guardare
# prova a elencare le cartelle da togliere PRIMA di leggere sotto

rm -rf _bmad/
rm -rf .claude/skills/bmad-*      # o la cartella del tuo strumento
# _bmad-output/ contiene il TUO lavoro: decidi tu
# AGENTS.md può contenere righe non messe da BMAD: guardalo prima

# l'orchestratore, se c'era
rm -rf .bmad-loop/
rm -rf ~/.local/state/bmad-loop/
WSL
rm -rf _bmad/
rm -rf .claude/skills/bmad-*
rm -rf .bmad-loop/
rm -rf ~/.local/state/bmad-loop/
Windows · PowerShell
Remove-Item -Recurse -Force _bmad\
Remove-Item -Recurse -Force .claude\skills\bmad-*
Remove-Item -Recurse -Force .bmad-loop\
Remove-Item -Recurse -Force $env:LOCALAPPDATA\bmad-loop\state\
Le tre cose che restano, e vanno tolte a mano Le voci aggiunte al .gitignore; gli hook registrati nel file di impostazioni della tua CLI; e le eventuali skill installate globalmente nella home, che non appartengono a nessun progetto e quindi nessuna rimozione di progetto le tocca. Quest'ultima è la più insidiosa: rimuovi BMAD da un progetto, continui a vedere le skill, e non capisci perché.
Diagnosi

Quando non funziona

I sintomi che si presentano davvero in aula, con la causa quasi certa. Da tenere aperto sul proiettore durante il laboratorio.

SintomoCausa quasi sempre, e cosa fare
L'installazione riesce, la prima skill si arrestauv non è nel PATH. L'installer avvisa ma non blocca — puoi vedere verde e poi fermarti. Installa uv, riapri il terminale, riprova: non serve reinstallare.
«Installato in una cartella che non ho mai digitato»Era un difetto noto del prompt della cartella, corretto: il campo restituiva l'opzione evidenziata dal completamento invece del testo digitato, e un singolo tasto freccia selezionava silenziosamente l'ultima directory dell'elenco. Se ti capita, stai usando una versione vecchia dell'installer.
Un modulo è sparito dopo un aggiornamento--modules non è un delta: è l'insieme esatto finale. Rielenca tutti i moduli che vuoi tenere.
La CLI non vede le skillSono nella cartella di un altro strumento. Controlla con --list-tools qual è la destinazione della CLI che stai usando e reinstalla con il --tools giusto.
Ho personalizzato una skill e l'aggiornamento ha cancellato tuttoHai modificato il customize.toml della skill invece di creare un file in _bmad/custom/. È la ragione per cui l'esercitazione 4 viene prima delle altre.
L'orchestratore va in timeout subitoLa CLI di coding non è mai stata avviata in quel progetto e sta aspettando la conferma di fiducia del workspace. Avviala a mano una volta e accetta i dialoghi.
Un run non presidiato si rifiuta di partireFile di personalizzazione con un nome deprecato. Lo shim propone la migrazione ma pretende un'approvazione esplicita, che una sessione non presidiata non può dare, quindi si ferma invece di inoltrare. Rinomina il file a mano.
Dentro WSL sembra tutto WindowsHai installato gli strumenti con l'interprete Windows: sono raggiungibili dal prompt bash e si comportano silenziosamente come Windows. Il comando che elenca i backend deve riportare linux come default di piattaforma; se dice win32, reinstalla dentro Linux.
Ho aggiornato l'orchestratore ma è tutto come primaSu una sorgente git l'aggiornamento normale riusa il commit in cache. Serve --reinstall. E ricorda il secondo passo: ristendere le skill in ogni progetto.
Tutto è lentissimo su WindowsStai lavorando su /mnt/c/… da WSL. Sposta il repository dentro il filesystem Linux.
